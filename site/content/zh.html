01研究概览

Valibra 在原 BIRD-Interact Agent 前增加信息整理与检查流程：先确定表范围、连接关系、字段对应与业务知识，再让 Main 编写 SQL。主流程无法完成时，在剩余预算内判断是否启动独立补救。

这是阶段性研究成果，不是整体性能领先的声明。相同 600 题中，P1 与 Reward 略有提高，但完整任务通过数下降，总 token 消耗增加。

本站是适合公开分享的中俄双语摘要，保留报告的章节和折叠案例形式。完整状态快照、原始模型输出与逐题 SQL 留在组内材料中，不随网站发布。

02框架设计与实现

“四维”指四类信息，不是四个独立 Agent。Structure 同时负责表与连接关系；Check 和 Gate 是检查与路由环节，不属于四维信息本身。

维度负责环节保存内容
tablesStructure候选表范围，不要求最终 SQL 使用全部候选表。
join_keysStructure表之间的连接关系。
column_mappingMapping请求短语与字段或完整 JSON 路径的对应。
domain_knowledgeKnowledge有来源的业务定义、计算公式及规则。

Check：信息是否足够，而非答案是否正确

Check 检查字段、公式、筛选条件与输出要求。存在缺口时，每次最多申请一个补查动作，包括字段说明、知识查询、受限制的只读 SQL 或用户澄清。运行程序再校验预算、重复请求与权限。

普通 Check 的结果下一步
完成，complete进入 Gate，判断新证据是否要求修订信息。
未完成，且有获准的下一工具补查后再 Check，暂不进入 Gate。
未完成，next_tool = null进入 Gate，判断是否有依据重做或应当结束。

Gate 与草稿：决定范围，隔离未完成修改

Gate 接收当前四维信息、Check 结果与缺口、澄清和证据，只决定重做范围。字段重做走 Mapping → Knowledge → Check；表范围重做先经过 Structure。

修改先保存在临时草稿，检查与提交校验通过后才整体更新正式状态。草稿失败时回滚；合法的用户澄清先丢弃草稿再提问，回答后重新建立草稿。

NO_REGROUND 不等于检查通过。只有 Check 已完成才进入正常 Main；未完成且无法推进时结束主流程。循环受证据、预算与调用上限约束，不会无限重试。

Main 与独立补救

Main 接收请求、四维摘要、已回答澄清及公开执行要求，只保留 execute_sql 与 submit_sql。完整 schema、字段说明和补查历史并不会全部传入 Main。

主流程返回后，外层在补救已启用、任务未完成、阶段与余额有效、剩余至少 3 Coin 且本题尚未补救时，启动一次独立的原 Agent 会话。补救恢复九个工具，沿用余额和已通过的 P1 产物，不重置预算，也不返回四维主流程。

03实际案例分析

按“输入 → 决策 → 状态变化 → 结果”展开。以下为匿名化过程摘要，不公开原始响应或答案。

CASE A · PRIMARY SUCCESS公式取证、字段重做与两阶段成功

一项通信统计任务需要先计算密度，再根据后续问题改变聚合方式。主要难点是将已有公式与实际字段对应起来。

  1. Structure → Mapping：确定单表范围；Mapping 暂不猜测计算字段，将缺少规则保留为未解决项。
  2. Knowledge：取得公式并保存知识。模型同时提出的字段修改不在该阶段权限内，未直接写入正式状态。
  3. Check → Gate：补查后仍需 Mapping 处理操作数；Check 未完成且无下一工具，Gate 选择局部字段重做。
  4. 临时草稿：Mapping 对应公式操作数并清除过时的未解决项；Knowledge 保留公式；Check 通过，草稿统一提交。
  5. P1 → P2：正常 Main 完成第一阶段；后续问题只改变聚合方式，复用已确认的信息，两阶段均通过。
1 次草稿提交、0 次回滚，未启动补救。这说明权限控制与修订链路可以共同完成任务，不代表每次模型输出都被直接接受。

本题基线也通过，不能作为净增分证据；流程中仍有重复取证，不能据此宣称成本更低。

CASE B · FALLBACK SUCCESS澄清保留、草稿回滚与独立补救

一项设备质量分析任务同时存在指标定义与类别程度两处歧义。

  1. 初始整理：表与字段范围已确定，但质量指标不明确，Mapping 保留用户意图缺口。
  2. Check 澄清：用户明确指标的计算方向；回答单独保存，不自动改写字段映射。
  3. Gate → 草稿：局部重做 Mapping 与 Knowledge，将新定义落实到计算字段。
  4. 交接失败：草稿 Check 申请进一步确认类别，但请求缺少交接要求的分类信息，运行程序拒绝执行并丢弃草稿。
  5. 独立补救：原 Agent 继承正式状态、已有澄清与剩余预算继续处理，最终两阶段通过。
澄清保留与草稿隔离正常工作，但最终成功来自补救，不能计为主流程或草稿提交成功。

部分类别解释未获用户明确确认；数值表示也可能影响评测。最终 PASS 不能单独证明语义解释唯一正确。

CASE C · FINAL FAILURE字段已对应，类别证据却未传入 Main

一项节目分类查询需要返回标识、名称和类别，并按名称排序。

  1. Structure / Mapping：选对表、名称和类别字段，前序字段说明中也包含实际枚举值。
  2. Knowledge / Check：没有保留相关定义；类别条件尚未完全落实，Check 却返回完成。
  3. Gate → Main：Gate 不重做。Main 收到字段映射，但没有收到此前取得的枚举说明。
  4. SQL 修改：Main 修正实现错误，并多次尝试类别值，但没有补齐缺失的语义证据。
  5. 结果：P1 未通过，无法进入 P2；余额不足，未启动补救。
“前序已查到”不等于“后序已收到”。Check 通过也不能保证信息交接完整，最终成败不能单独归于 SQL 编写阶段。

三个案例分别展示主流程成功、补救成功和最终失败，不构成三类路径成功率的统计比较。

05限制与后续方向

600 条最终计分记录中有 18 条经授权的替代运行。用量只包含最终计分尝试中已报告的部分，不含作废尝试、开发实验或基础设施；20 次 Grounding 尝试未返回 usage，不能当作零成本。

两侧运行日期、阶段输出上限和重试政策并不完全相同，部分题曾用于开发。本轮同题结果不证明统计显著性，也不证明未知任务上的普遍优势。

发布代码包含后续审计存储修复，但没有重跑 600 题。本站成绩对应原冻结评测版本，不应解释为每次后续代码变动的最新成绩。
  1. 统一 Grounding、Main、补救与用户模拟器的用量统计。
  2. 减少广域取证和重复长推理，按实际缺口补查。
  3. 检查关键信息是否真正传入下一阶段。
  4. 同时评估新增收益、原有成功题保留、完整通过率与成本。
  5. 保留未用于开发的测试集，开展同题配对验证。

下一阶段重点是减少重复工作与信息丢失、保留正常路径，而不是未经验证地扩展状态或叠加语义检查模型。
